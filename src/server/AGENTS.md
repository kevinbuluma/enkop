# Backend rules (master database, mirror sync, privileged work)

- The ENKOP master is the Cloudflare Worker `enkop` backed by ENKOP's own Supabase project (`enkop`, eu-west-2): Postgres reached through the Hyperdrive binding `HYPERDRIVE` (query caching disabled so every read sees the latest write) (`pg` driver, src/server/backend/pg.ts behind the D1-style `prepare/bind/all/first/run/batch` interface) and media in its private `property-media` Storage bucket (ENKOP_SUPABASE_URL / ENKOP_SUPABASE_SERVICE_KEY). It is the single source of truth; Lovable Cloud is a mirror kept in sync automatically. The old D1 `enkop-db` and KV namespace are kept read-only as a rollback. Public catalogue reads published records and enquiries are written through validated server functions so the presentation stays separate from data access.
- Privileged work (media signing, enquiry insert + WhatsApp alert, AI Gateway) goes through src/integrations/supabase/privileged.server.ts: direct when managed keys exist, otherwise via the secret-authenticated /api/public/enkop-bridge route on Lovable hosting (ENKOP_BRIDGE_SECRET, optional ENKOP_BRIDGE_URL) so non-Lovable hosts work without holding managed keys.
- Data access goes through `getBackend()` (public reads, media signing, enquiries) and `getMaster()` / the `requireAdmin` middleware in src/lib/require-admin.ts (admin reads and writes) from src/server/backend. Never query Supabase directly from route or `*.functions.ts` code: on the master those calls would read the stale mirror.
- Master writes go through `MasterStore` (`upsert`/`update`/`remove`/`run`). The `enkop_outbox()` trigger on every content table queues each insert/update/delete (including dashboard edits) in the master `outbox` in the same transaction; media and alerts are queued by code. The outbox is drained to the mirror via the bridge `mirror/*` routes after each write, on traffic, and by the pg_cron jobs `enkop-master-drain` in both Supabase projects. Rows copied from the mirror set `enkop.skip_outbox = 'on'` for their transaction (`MasterStore.importRow`). SQL must use `?` placeholders and never the jsonb `?` operators.
- Outbox drains to the mirror hold a single `mirror-drainer` lease in `meta` (renewed per row) so deliveries never interleave; a row that fails 20 times is set aside (done, error kept, counted as `setAside` in status) instead of blocking later changes. The daily `enkop-housekeeping` pg_cron job prunes delivered non-delete outbox rows after 30 days, expired sessions and old cron history.
- Public enquiries (both entry points) and admin sign-in/setup are rate-limited with the Workers Rate Limiting bindings `ENQUIRY_LIMITER` / `SIGNIN_LIMITER` via src/server/rate-limit.ts (no binding means no limit, e.g. on Lovable). The mirror forwards the visitor address as `x-enkop-client-ip`, trusted only with the bridge secret. Enquiry validation lives in src/lib/enquiry-schema.ts and is shared by the form and the server; messages shown to visitors come from `enquiryProblem`.
- Lovable is the fallback, never a second writer: on the master, `getBackend()` wraps the master database with `withMirrorFallback` (public reads from the mirror, enquiries stored in Lovable Cloud if the master fails), and cloudflare/entry.mjs serves the Lovable-hosted page when a public page fails (server functions only on 502–504; admin, media and `/api/public/enkop-*` never fall back). Enquiries stored on Lovable are pulled back by `pullMirrorEnquiries` (bridge `mirror/enquiries`) on every drain and alerted from the master.
